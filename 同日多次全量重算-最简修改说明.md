# 同一天多次全量重算：最简修改说明

依据：`acbcee8`，Java 实现为 `f523d4a`。本文只提供修改办法，未修改生产 Java、SQL 或数据库。

## 1. 最终行为与实现选择

算法版本继续用 V1。每次触发都重新计算本次有效户号的全天 96 点，覆盖当天 MySQL、TDengine 的旧结果，包括旧修正结果。

采用“重建当天明细和修正任务”：同日运行记录仍保留一条，使用现有 execution_owner 区分执行者；每轮删除旧明细、旧任务并重新插入，旧任务 ID 失效。无需新增表、业务版本或轮次字段。

保留现有日期+版本唯一约束、原子领取和租约。重算期间当天修正暂停；跨 Pod 发布锁只用于清理、单户发布和结束收口，不锁住整天的计算。

每次重新触发（包括上次失败后的再次触发）都是全量重算，不再复用上一轮的点明细。

| 文件 | 具体改动 |
| --- | --- |
| UserBaselineRunMapper.java | SUCCESS 可重新领取；刷新本轮时间和计数；新增可修正运行记录的锁定查询 |
| UserBaselineGenerationService.java | 取消 SUCCESS 拒绝；开始时清理当天数据；每户固定计算 96 点；结束时调用事务收口 |
| UserBaselinePersistenceService.java | 增加清理与收口事务；生成明细直接批量插入；修正保存同时检查当天运行状态 |
| UserBaselineDetailMapper.java | 新增当天明细物理删除方法 |
| UserBaselineCorrectionTaskMapper.java | 新增当天任务物理删除；查询、领取仅允许已结束生成的日期 |
| UserBaselineInitialWindowMapper.java | 只清理本次业务日创建的首次初始化窗口 |
| UserBaselinePublisher.java | 新增完整 96 点发布入口，校验生成执行权，并复用现有 replaceUserDate |

没有要求修改 Handler 的任务参数或增加一个新算法版本。现有 UserBaselineLoadStore、TDengine XML 的按日期替换方法可复用。

## 2. RunMapper：允许再次领取，保留并发保护

替换 `claimForProcessing` 的 SQL 和签名，增加 LocalDateTime 的 import：

```java
@Update("UPDATE ra_user_baseline_run SET status='RUNNING',execution_owner=#{owner},"
        + "lease_expire_time=TIMESTAMPADD(SECOND,#{leaseSeconds},NOW(3)),heartbeat_time=NOW(3),"
        + "total_user_count=#{total},success_user_count=0,failed_user_count=0,"
        + "snapshot_time=#{snapshotTime},started_at=NOW(3),finished_at=NULL,error_message=NULL,"
        + "last_modify_time=NOW(3) WHERE id=#{id} AND deleted=0 AND (status IN "
        + "('SUCCESS','FAILED','PARTIAL_FAILED') OR (status='RUNNING' AND lease_expire_time<=NOW(3)))")
int claimForProcessing(@Param("id") Long id, @Param("owner") String owner,
                       @Param("leaseSeconds") int leaseSeconds,
                       @Param("total") int total,
                       @Param("snapshotTime") java.time.LocalDateTime snapshotTime);
```

在 `acquireRun` 中，原来的 `existing == null || SUCCESS` 判断改为只检查 `existing == null`；领取调用增加 `total, snapshotTime`。影响行数不是 1 时仍拒绝执行，不能绕过未过期的 RUNNING。

新增以下查询，用于修正保存事务锁住运行记录。它与生成领取共同保证：修正保存检查通过后，生成不能在该保存事务结束前切入。

```java
@Select("SELECT * FROM ra_user_baseline_run WHERE data_date=#{dataDate} "
        + "AND calc_version=#{calcVersion} AND deleted=0 "
        + "AND status='SUCCESS' FOR UPDATE")
UserBaselineRun selectReadyForCorrectionForUpdate(
        @Param("dataDate") java.time.LocalDate dataDate,
        @Param("calcVersion") String calcVersion);
```

## 3. 三个 Mapper：增加清理方法

以下均为显式物理 DELETE，不使用逻辑删除。否则原有唯一键可能挡住本轮重新插入。各文件增加 `org.apache.ibatis.annotations.Delete` import。

**UserBaselineDetailMapper：**

```java
@Delete("DELETE FROM ra_user_baseline_detail "
        + "WHERE data_date=#{dataDate} AND calc_version=#{calcVersion}")
int deleteDayForRebuild(@Param("dataDate") java.time.LocalDate dataDate,
                       @Param("calcVersion") String calcVersion);
```

**UserBaselineCorrectionTaskMapper：**

```java
@Delete("DELETE FROM ra_user_baseline_correction_task "
        + "WHERE data_date=#{dataDate} AND calc_version=#{calcVersion}")
int deleteDayForRebuild(@Param("dataDate") java.time.LocalDate dataDate,
                       @Param("calcVersion") String calcVersion);
```

**UserBaselineInitialWindowMapper：**

```java
@Delete("DELETE FROM ra_user_baseline_initial_window WHERE calc_version=#{calcVersion} "
        + "AND first_target_time>#{startTime} AND first_target_time<=#{endTime}")
int deleteDaySeedsForRebuild(@Param("startTime") java.time.LocalDateTime startTime,
                           @Param("endTime") java.time.LocalDateTime endTime,
                           @Param("calcVersion") String calcVersion);
```

初始化窗口不是当天的 96 点明细，只清理 `first_target_time` 属于本次业务日的记录。其他历史日期的初始化窗口和已发布基线不全库清理。业务日边界沿用当前规则：`当天00:00 < ts <= 次日00:00`。

## 4. PersistenceService：准备、保存、收口各用短事务

### 4.1 增加公共执行权检查和准备方法

```java
@Transactional(rollbackFor = Exception.class)
public void assertGenerationOwner(Long runId, String owner) {
    requireGenerationOwner(runId, owner);
}

private void requireGenerationOwner(Long runId, String owner) {
    if (runMapper.selectOwnedActiveForUpdate(runId, owner) == null) {
        throw new IllegalStateException("生成任务已失去执行权，运行ID=" + runId);
    }
}

@Transactional(rollbackFor = Exception.class)
public void prepareFullRebuild(Long runId, String owner,
                               java.time.LocalDate dataDate, String calcVersion) {
    requireGenerationOwner(runId, owner);
    taskMapper.deleteDayForRebuild(dataDate, calcVersion);
    detailMapper.deleteDayForRebuild(dataDate, calcVersion);
    initialWindowMapper.deleteDaySeedsForRebuild(
            dataDate.atStartOfDay(), dataDate.plusDays(1).atStartOfDay(), calcVersion);
}
```

这三次删除与执行权检查在同一个事务中。只有获取本轮执行权并成功清理后才开始保存新明细。旧任务被删除，新任务使用新的自增 ID；旧修正执行者不能凭旧 taskId 更新本轮数据。不要 TRUNCATE 表、重置自增计数或复用旧 ID。

### 4.2 替换 saveGeneratedDetails

删除原来的“查询已有明细、仅插入 missing”逻辑，直接批量保存本轮计算结果：

```java
@Transactional(rollbackFor = Exception.class)
public void saveGeneratedDetails(Long runId, String owner,
                                  List<UserBaselineDetail> details) {
    requireGenerationOwner(runId, owner);
    if (details == null || details.isEmpty()) {
        return;
    }
    int batchSize = Math.max(1, properties.getDetailWriteBatchSize());
    for (int start = 0; start < details.size(); start += batchSize) {
        detailMapper.insert(details.subList(
                start, Math.min(start + batchSize, details.size())));
    }
}
```

新对象没有上一轮 K、窗口 JSON、修正时间；本轮按原 calculateUser 填 B0、样本、剔除信息、needCorrection、初始状态、当前值和 PENDING。不要把旧实体读出来再赋几个字段。

### 4.3 替换 requireTask：先锁运行记录，再锁任务

增加 UserBaselineCorrectionTask 的 import。

```java
private void requireTask(Long taskId, String owner) {
    UserBaselineCorrectionTask task = taskMapper.selectById(taskId);
    if (task == null) {
        throw new IllegalStateException("修正任务已失效，任务ID=" + taskId);
    }
    if (runMapper.selectReadyForCorrectionForUpdate(
            task.getDataDate(), task.getCalcVersion()) == null) {
        throw new IllegalStateException("当天正在重算或生成未完成，暂停修正");
    }
    if (taskMapper.selectOwnedActiveForUpdate(taskId, owner) == null) {
        throw new IllegalStateException("修正任务已失去执行权，任务ID=" + taskId);
    }
}
```

现有 saveInitialWindows、saveCorrections 都已在事务中调用 requireTask，继续保留。统一“run → task → detail”的加锁顺序，不反过来锁，以免与重建事务互相等待。

### 4.4 把任务创建和生成完成放进一个有执行权检查的事务

增加依赖 `private final UserBaselineStorageSupport storageSupport;`，以及 UserBaselineSlotSummary 的 import。新增：

```java
@Transactional(rollbackFor = Exception.class)
public int finishFullRebuild(Long runId, String owner,
                             java.time.LocalDate dataDate, String calcVersion,
                             int success, int failed) {
    requireGenerationOwner(runId, owner);
    List<UserBaselineSlotSummary> summaries =
            detailMapper.selectCorrectionSlotSummaries(dataDate, calcVersion);
    int correctionPoints = 0;
    for (UserBaselineSlotSummary summary : summaries) {
        int slot = summary.getSlotNo();
        int total = summary.getTotalCount() == null ? 0 : summary.getTotalCount();
        if (slot < 1 || slot > UserBaselineConstants.POINTS_PER_DAY || total <= 0) {
            throw new IllegalStateException("修正任务点位或数量非法");
        }
        java.time.LocalDateTime targetTime = storageSupport.slotTime(dataDate, slot);
        taskMapper.insert(UserBaselineCorrectionTask.builder()
                .dataDate(dataDate).slotNo(slot)
                .targetTime(targetTime).scheduledTime(targetTime)
                .status(UserBaselineConstants.TASK_PENDING)
                .totalCount(total).successCount(0).failedCount(0).retryCount(0)
                .calcVersion(calcVersion).build());
        correctionPoints += total;
    }
    String status = failed == 0 ? "SUCCESS" : "PARTIAL_FAILED";
    if (runMapper.complete(runId, owner, status, success, failed) != 1) {
        throw new IllegalStateException("生成收口时执行权已失效，运行ID=" + runId);
    }
    return correctionPoints;
}
```

旧任务已在 prepareFullRebuild 删除，所以收口只创建本轮任务，不复用旧任务，也不再调用原 reconcileCorrectionTasks。将这个原私有方法从 GenerationService 移除，避免旧执行者绕开 owner 检查改写新任务计数。

## 5. TaskMapper：RUNNING 期间不查询、不领取当天任务

在 selectDueRecoverable 和 claimForProcessing 原 SQL 的 WHERE 逻辑末尾，追加以下条件（ORDER BY/LIMIT 之前）：

```sql
AND EXISTS (
    SELECT 1 FROM ra_user_baseline_run r
    WHERE r.data_date = ra_user_baseline_correction_task.data_date
      AND r.calc_version = ra_user_baseline_correction_task.calc_version
      AND r.deleted = 0
      AND r.status = 'SUCCESS'
)
```

两个 SQL 的原状态条件必须保留括号，再用 AND 拼接；不要只改查询、不改原子领取。本方案仅在 SUCCESS 后开放当天修正：RUNNING、FAILED、PARTIAL_FAILED 均暂停。这样先保证本轮原始 96 点全部替换成功，再处理 K；发生部分失败时再次触发全量重算。

对已经在运行的旧修正任务，最终靠第 4.3 节的事务检查和旧 taskId 失效阻止保存。只在任务入口查一次状态不够。

## 6. GenerationService：清理一次，每户固定计算 96 点

新增依赖：

```java
private final UserBaselinePublicationMutex publicationMutex;
```

### 6.1 准备阶段

acquireRun 按第 2 节允许再次领取。进入现有心跳 try 块后，保留日历和候选范围检查，在用户分页 while 循环之前执行一次：

```java
publicationMutex.execute(() -> {
    persistenceService.prepareFullRebuild(
            run.getId(), executionOwner, dataDate, calcVersion);
    return null;
});
```

它使用现有跨 Pod 发布锁，避免旧发布已经读出记录时被清理、新旧结果交错。只在本轮开始调用一次，不能在每个户号或分页批次都清理当天。

### 6.2 完整替换 processBatch：移除复用分支

使用现有类型、字段和 helper 方法，替换为：

```java
private BatchResult processBatch(Long runId, String executionOwner,
                                 LocalDate dataDate, BaselineCalendarDay targetDay,
                                 List<BaselineCalendarDay> historyDays,
                                 List<BaselineCalendarDay> sourceDays,
                                 List<AggregateUser> users, LocalDateTime snapshotTime) {
    List<String> consNos = users.stream().map(AggregateUser::getConsNo)
            .filter(value -> value != null && !value.isBlank()).distinct().toList();
    List<String> dataDates = sourceDays.stream()
            .map(day -> day.getCalendarDate().toString()).distinct().toList();
    List<UserLoadPoint> sourcePoints = consNos.isEmpty() || dataDates.isEmpty()
            ? List.of() : sourceMapper.selectByConsNosAndDates(consNos, dataDates);
    Map<String, Map<LocalDate, Map<Integer, UserLoadPoint>>> loads = groupLoads(sourcePoints);
    Map<String, Set<LocalDate>> participationByUnit = participationDates(users, sourceDays);

    Set<Integer> slots = new LinkedHashSet<>();
    for (int slot = 1; slot <= UserBaselineConstants.POINTS_PER_DAY; slot++) {
        slots.add(slot);
    }
    int failed = 0;
    List<String> calculatedUsers = new ArrayList<>(users.size());
    List<UserBaselineDetail> generatedDetails = new ArrayList<>();
    for (AggregateUser user : users) {
        if (user.getConsNo() == null || user.getConsNo().isBlank()) {
            failed++;
            continue;
        }
        try {
            UserRows calculated = calculateUser(runId, dataDate, targetDay, historyDays, user,
                    participationByUnit.getOrDefault(user.getUnitId(), Set.of()),
                    loads.getOrDefault(user.getConsNo(), Map.of()), snapshotTime, slots);
            if (calculated.details().size() != UserBaselineConstants.POINTS_PER_DAY) {
                throw new IllegalStateException("本轮必须重新计算完整96点");
            }
            generatedDetails.addAll(calculated.details());
            calculatedUsers.add(user.getConsNo());
        } catch (Exception e) {
            failed++;
            log.error("[用户基线] 全量重算失败，户号={}，日期={}",
                    user.getConsNo(), dataDate, e);
        }
    }
    persistenceService.saveGeneratedDetails(runId, executionOwner, generatedDetails);
    List<UserBaselineDetail> persisted = consNos.isEmpty() ? List.of()
            : detailMapper.selectList(new LambdaQueryWrapper<UserBaselineDetail>()
                    .eq(UserBaselineDetail::getDataDate, dataDate)
                    .eq(UserBaselineDetail::getCalcVersion, properties.getCalcVersion())
                    .in(UserBaselineDetail::getConsNo, consNos));
    Map<String, List<UserBaselineDetail>> byUser = persisted.stream()
            .collect(Collectors.groupingBy(UserBaselineDetail::getConsNo));

    int success = 0;
    for (String consNo : calculatedUsers) {
        try {
            List<UserBaselineDetail> rows = byUser.getOrDefault(consNo, List.of());
            if (rows.size() != UserBaselineConstants.POINTS_PER_DAY) {
                throw new IllegalStateException("本轮持久化明细不足96点");
            }
            publisher.publishGeneratedUser(runId, executionOwner, dataDate, consNo,
                    rows.stream().map(UserBaselineDetail::getId).toList());
            success++;
        } catch (Exception e) {
            failed++;
            log.error("[用户基线] 全量发布失败，户号={}，日期={}", consNo, dataDate, e);
        }
    }
    return new BatchResult(success, failed);
}
```

它只在每批读取一次负荷，不读取上一轮计算明细；保存后的读取用于取得本轮实际入库 ID。每户传全部 96 个 ID 给新发布入口，不再从旧记录筛 missingSlots 或 PENDING 点。

### 6.3 结束阶段

删除现有“reconcileCorrectionTasks → runMapper.complete”的分开调用，改成一次事务收口：

```java
heartbeat.assertActive();
int completedUsers = success;
int failedUsers = failed;
correctionPoints = publicationMutex.execute(() ->
        persistenceService.finishFullRebuild(
                run.getId(), executionOwner, dataDate, calcVersion,
                completedUsers, failedUsers));
```

保留原 catch 中 releaseForFailure、心跳关闭和结果返回。不要给整个 generate 加事务。

## 7. Publisher：完整替换一户一天，清掉旧空值字段

新增 LocalDate、Comparator 的 import，新增以下入口。批量同步确认沿用已提交的《基线发布性能优化-基于运行日志.md》第 3—4 节；若尚未落地，需同时加入 confirmPublishedInBatches 及 Mapper 批量确认方法。

```java
public int publishGeneratedUser(Long runId, String owner,
                                java.time.LocalDate dataDate, String consNo,
                                List<Long> detailIds) {
    if (detailIds == null || detailIds.size() != UserBaselineConstants.POINTS_PER_DAY) {
        throw new IllegalStateException("全天发布必须提供96个明细ID");
    }
    publicationLock.lock();
    try {
        return publicationMutex.execute(() -> {
            persistenceService.assertGenerationOwner(runId, owner);
            List<UserBaselineDetail> rows = detailMapper.selectBatchIds(detailIds).stream()
                    .sorted(java.util.Comparator.comparing(UserBaselineDetail::getSlotNo))
                    .toList();
            boolean valid = rows.size() == UserBaselineConstants.POINTS_PER_DAY
                    && rows.stream().allMatch(row -> runId.equals(row.getRunId())
                            && consNo.equals(row.getConsNo())
                            && dataDate.equals(row.getDataDate())
                            && row.getSlotNo() != null && row.getSlotNo() >= 1
                            && row.getSlotNo() <= UserBaselineConstants.POINTS_PER_DAY)
                    && rows.stream().map(UserBaselineDetail::getSlotNo).distinct().count()
                            == UserBaselineConstants.POINTS_PER_DAY;
            if (!valid) {
                throw new IllegalStateException("本户全天明细不完整或不属于本轮目标");
            }
            loadStore.replaceUserDate(consNo, dataDate,
                    rows.stream().map(this::toLoad).toList());
            confirmPublishedInBatches(rows);
            return rows.size();
        });
    } finally {
        publicationLock.unlock();
    }
}
```

**为什么新入口复用 replaceUserDate，而不是继续省略空字段的 INSERT？** 你的日志中 NO_BASELINE 的 INSERT 没有 raw_baseline、final_baseline、K 等列。重算可能把原来非空的修正结果变成空值，不能仅凭该 INSERT 假定旧列一定被清空。

现有 replaceUserDate 已实现“本户业务日范围 DELETE，再插入完整 96 点”。在本轮原始基线发布时复用它，可避免依赖省略列或 NULL 更新的处理方式。时间范围沿用现有 XML 的 `ts > 当天00:00 AND ts <= 次日00:00`，不会误删其他日期。整户发布失败时 MySQL 仍有本轮完整 96 点和 PENDING 信息，不能确认未写成功的数据。

这个入口必须持有现有跨 Pod 锁，并验证 owner。否则失去执行权的旧生成线程可能删除新一轮已经发布的数据。不能在 GenerationService 取得跨 Pod 锁后再调用此入口，避免用另一个连接重复申请同一行锁。

普通逐点修正、修正失败补写继续走原 publish/publishCorrections 和 upsertPoints，不调用 replaceUserDate。因为本轮首次发布已经清除了旧 K 等字段，后续从 WAITING 更新为 CORRECTED/UNCORRECTABLE 仍沿用现有流程。

## 8. 执行顺序、失败行为与效率

```text
原子领取当天 run（置 RUNNING；有未过期执行者则拒绝）
    ↓
跨 Pod 锁内：短事务校验 owner，删除当天旧任务、旧明细及当天初始化窗口
    ↓
锁外：分页读取负荷，每户重新计算 96 点，MySQL 批量保存
    ↓
跨 Pod 锁内按户：校验 owner → 读取新96点 → TDengine替换本户当天 → 批量确认
    ↓
跨 Pod 锁内：短事务校验 owner → 创建本轮修正任务 → 标记 run结束
    ↓
分钟任务按时间顺序处理本轮到期点；未来点到时再修正
```

没有增加全天长事务或全天发布锁。性能仍使用每批 100 户、MySQL 批量插入、每户分组批量确认。全天替换每户增加一次 TDengine 范围 DELETE；相较原先 96 次逐点确认，先落地批量确认仍是最重要的提速措施。

每轮开始不提前删除 TDengine 全天所有户号的数据，新 B0 算出后才按户替换。它不是全日原子切换：重算中可能看到部分户号旧结果、部分户号新结果；单户 DELETE 后插入失败可能暂时缺点。此时运行状态不是完整成功，需要再次触发全量重算；不能把失败当作旧结果已经完整覆盖，也不能跳过全天替换、直接确认这一户生成成功。

旧 taskId、旧生成 owner 失效后，只能退出，不能保存本轮结果或创建本轮任务。FAILED、PARTIAL_FAILED 状态下均不继续当天修正。再次触发重算依然从清理开始；只有本轮全部生成及发布成功、run=SUCCESS，才恢复修正。这个全日完成屏障用于避免修正在旧 TDengine 数据尚未完整替换时提前运行。

“生成完成”表示本轮 B0 和修正任务已生成，不表示当天所有过去时点的 K 都已重新算完。当前 correctionTaskBatchSize=20，过去的到期任务会分批处理；修正继续遵循前置历史点完成的顺序。

## 9. 验收清单

1. 同日连续执行两次，第二次全部 96 点确实重新计算，不因旧明细存在而跳过。
2. 原来 NO_BASELINE 的点补入历史负荷后，重算能产生新 B0。
3. 原来 CORRECTED、K 非空，重算后 NOT_REQUIRED 或 NO_BASELINE：MySQL、TDengine 的旧 K、修正时间、窗口均不残留。
4. 重算时旧修正任务正在计算：旧 taskId 无法保存结果；生成结束后只执行新 taskId。
5. 另一个 Pod 同时触发同一天生成：只有一个未过期执行者获得执行权。
6. A 失去租约、B 接管后，A 不能清理、发布全天结果或收口改写 B 的任务。
7. TDengine 替换失败、同步确认失败均不能算本户成功；旧确认也不能匹配新明细 ID。
8. SQL 删除范围限定业务日和 V1，其他日期的数据不重算；00:00 跨日边界正确。
9. 有效户号计算仍每户 96 点；确认使用批量 SQL；修改前后用相同输入计时。
